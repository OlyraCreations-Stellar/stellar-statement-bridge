## Decisions and blockers
- Decisions: Research report created before selecting a product. Do not infer project quality from stars/forks. Do not claim Wave approval or production readiness. Keep Stellar use conditional on customer benefit. Similarity to existing projects is not disqualifying; a proposed project must show a meaningful, evidence-backed improvement. Reject a generic payout sender/dashboard due to official SDP overlap; the refined hypothesis is a single-repo ERPNext app importing successful Stellar SDP payments into statement-side Bank Transactions for native reconciliation. It will not create accounting vouchers or initiate payments. Consider upstream contribution if operators show that is the better route. Exclude incoming x402 receipts covered by Accensa.
- Blockers: Customer pain and final name remain unvalidated; no operator is currently available for interviews. Basic site installation, lifecycle, and native importer runtime behavior are verified, but no Olyra importer exists for comparison. ERPNext documentation confirms duplicate imports are a recognized risk, and its Plaid integration provides incremental transaction-ID sync; neither establishes a source-specific SDP gap. The host MariaDB root account remains untouched; use only the isolated disposable database.
- Risks: A repeated source transaction ID was not deduplicated in one ERPNext 16.53.0 fixture. Whether that matters to SDP users is unknown, and ERPNext already has an incremental bank-sync pattern through Plaid. An upstream enhancement may be preferable to a standalone connector. The verified behavior covers one version pair and one currency/amount case only. Program cycle and funding criteria may change.
